# LIP 深度组合检查

用户的长期要求：进一步细查各种组合、次序、逻辑、竞争、条件、递归及其边界、兼容、误解和不直观行为；发现问题就处理，不以时间成本代替检查结论。此流程补充[开发指南](../../DEVELOPMENT.md)，不要求对每次小改动展开全语言审计。

先读当前中英文 1.1 规范的相关章节，区分语言保证、明确的保守分析界线、实现缺陷和文档误导。1.0 是历史规范，工程版本号不随审查改变。Flow 定义不是值；run 内普通值可跨 Flow，Host、Claim 和外部入口仍递归要求 Data；fn 的计算结果与业务效果纯性、Flow 无环和规范 Ops 不因实现便利而放松。

## 选择有语义风险的交叉组合

从真实程序和本次改动建立矩阵，优先覆盖会共享状态、改变效果或丢失信息的交点，避免无目的的全排列：

- 值与通道：Data、function、effect、nullable、混合容器，经参数、返回、字段/下标、捕获、管道、循环、模块和 session cell 传递。
- 控制与调用：直接/动态/高阶调用、命名实参、短路、if/match、零次循环、carry、直接/互递归及尾调用；未选路径不得有动态错误或外部动作。
- 调度与身份：依赖、ReadOnly 重叠、Write/Unknown barrier、父子图、After、额度为 1 的活性、取消、失败前置闭包、Claim 身份和重放；改变并行度不应改变规范结果。
- 生命周期：子图释放后闭包仍有效，冻结捕获不随删除/复用名字变化；snapshot 绑定原 run/Flow 实例；失败 cell 不提交绑定，也不声称能回滚已执行动作。
- 分析界线：RetOps 与执行 Summary 分开，实参效果不能被 Pure callee 隐藏；原生来源仅描述返回位置，不把所有实参混入结果，不借来源分析增强规范并行权限。

对递归分析检查终止性、单调性及声明顺序/私有名称无关性。对混合容器检查纯字段、固定下标和覆盖后的字段不被邻近资源污染。元数据不能延长业务值或 AST 的寿命。显式原生调用的接收者可能藏在含 fn/effect 的普通对象中；只固定成员路径所需的包装字段，不能把整个混合容器送到 Host，也不能因此豁免实际参数的 Data 检查。原生属性与缺失成员错误仍延迟至 perform。

After 与局部游标交叉时，已跳过分支/短路及已完成循环中的调用不再保留未来 owner 依赖；活动循环的单轮完成不能提前关闭整个调用集合。批量处理事件后先刷新完成集合，再判环。对嵌套实参和独立绑定分别检查顺序/并发，不能为缩行改变工作间的重叠机会。

## 用可观察行为证明

先构造最小复现，再修改实现，为每个实际修复保留回归。断言具体输出、诊断代码/归属、调用次数和必需的先后关系，不能只比较两条路径是否同样出错。

调用失败顺序应为：callee → callable/arity/命名参数 → 源码顺序实参 → 参数注解 → body → 返回注解。检查错误前不应发生的 provider 调用确为零；动态参数类型检查发生在全部实参求值后。

通过交换声明、重命名私有函数、改变并行度和等价封装做变形检查；仅在规范保证等价时要求结果不变。源码变化会改变位置/CallID，不要求它们跨源码不变。递归随机生成器需固定种子、限制结构规模，并验证实际覆盖的编译/运行路径；普通 fuzz 未启用 NativeHost 时不能宣称覆盖 native lowering。

成功和失败组合均比较解释器、实际构建运行的 Go 程序与适用的 session/跨模块路径。并发重叠用 provider rendezvous 或事件关系证明，避免仅靠睡眠和耗时阈值；共享测试状态也需通过 race。生成程序同样启用竞争检测。

诊断检查按 §3.2 区分计算不干扰与日志可观察性：覆盖开/关/满/关闭/故障/阻塞接收端、共享缓冲并发关闭、预算和取消；比较返回值、错误、Steps、journal、RetOps 和真实并行。实参不能因禁用而省略，包含 perform 的实参仍有业务效果；未选路径、声明、编译与补全零发送。检查跨模块/闭包/容器中的诊断函数、资源释放后的不透明显示、失败 cell 已发诊断和旧捕获。事件不得留住业务值、闭包、AST 或原生对象；显示处理本身也要有界，不能为识别不透明引用而先构造巨型描述。新增核心函数时检查名称兼容性，不能笼统声称旧合法代码全部兼容。

## 同步与交付

用真实应用检验新组合能力，比较改写前后的主文件和总实现行数，将结构收益与缩行收益分开报告；保留校验、资源关闭、流式和交互行为。泛化为 effect 参数后，不假定 perform 结果仍有静态原生来源；动态 Python 属性用显式 getattr，方法用显式 receiver 请求。用可观察事件验证构造零调用、重复 perform 和每次清理。测试编译与各执行模式分别计时，不能让先前阶段耗尽后续交互检查的预算。

修复后核对中英文 spec、README、帮助、learn、示例与实现的接受条件和错误说明。特别说明动态 effect 的 Unknown、nullable 不自动收窄、入口 Data 边界和显式原生 receiver 请求，避免例子暗示不存在的保证。

区分不可变值与增量构造：先实跑 carry + concat/put，再判断是否缺少容器更新能力。覆盖多批初始状态、空输入、重复列表项、同名键覆盖、旧值保留，以及 Flow 先 perform 再 next 的路径；说明 concat 的复制成本，不能暗示常数时间追加。应用选择启动时构造一次，不代表语言只能一次性生成。讨论放宽纯性时，分别分析返回值的确定性与日志等可观察效果，不将“返回值可推导”等同于可任意缓存、消除或重试调用。

完整测试开始前固定源码、fixture 与预期；运行期间修改它们会使编译快照与运行读取不一致，不能把这种失败当作语言缺陷或忽略最终重跑。完成相关回归、文档一致性、`make test`、`make race`、`make vet`；代码变动后不能用旧日志充当最终验证。记录实际覆盖、被环境跳过的路径和剩余分析界线，不承诺消除一切潜在 bug。运行 `make clean` 清理项目产物。
